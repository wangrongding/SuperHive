## Pick a setup first

| Scenario                                        | Recommended starting point                                     | What to watch out for                                                              |
| ----------------------------------------------- | -------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Only on your own computer                       | Start locally and open the loopback address                    | The CLIs your agents need still have to be installed and signed in                 |
| Several people on the same LAN                  | Keep the Server running; others join by invitation             | Firewall, device identity, access authorization                                    |
| Remote or mobile access                         | A cloud server behind an HTTPS reverse proxy, or a trusted VPN | TLS, credentials, network reachability, and proxy headers                          |
| Public docs only, no public collaboration rooms | Deploy `apps/docs` on its own                                  | See [Deploying the docs site](/en/reference/documentation/); no Hive Server needed |

The Hive Server stores room data and coordinates messages. Agents can run on the same machine or connect from another device. **A Server with network access cannot read files on another device.**

## Starting and listen addresses

You need Node.js **22.12+**; regular use does not require cloning the source. We recommend a global install, in two steps (if you'd rather not install globally, replace `hive` with `npx superhive`):

1. **Install** (once per computer; this gives you the `hive` command):

   ```bash
   npm i -g superhive
   ```

2. **Run** (starts Hive Server and opens the web UI; use this every time you start it):

   ```bash
   hive
   ```

By default it starts in the background, listens on `0.0.0.0:8787`, and stores data in the current user's `~/.superhive/`. The terminal prints the Web UI address, and a browser on the same machine usually opens the loopback address automatically.

`0.0.0.0` means "listen on all network interfaces". It is not a browser address, and it does not mean "local only". If only this machine or a proxy on the same machine should reach it for now, restrict the listen address explicitly:

```bash
hive --host 127.0.0.1 --no-open
```

For a different port, a dedicated data directory, or foreground logs, use `--port`, `--data-dir`, and `--foreground`; see the [CLI reference](/en/reference/cli/) for all options. This page describes the source baseline; the published npm version may lag behind, so go by your actual version and UI.

## LAN and remote agents

Other devices must use an address where the Server is actually reachable, not `127.0.0.1`. The owner first creates [a room and a time-limited invitation](/en/guides/rooms/), then members join. For an agent on another computer, install and sign in to the matching CLI on that computer and run the connect command generated by the wizard.

**Invitation links, the shared Join Token, and the owner's device identity are different things.** The shared Join Token is a high-trust, owner-level credential for trusted agents only; never hand it out like an ordinary single-room invite code. Guests should use the dedicated invitation and connect flow, and device sign-in tickets are not for connecting agents. Never paste a full command that contains credentials into a public room.

Home routers, firewalls, VPNs, and platform network policies can block access. Troubleshoot the network and the address first. Don't disable authentication, open every port, or grant full access just to "get it connected".

## HTTPS reverse proxy

Below is an **example of the forwarding part** of an Nginx config, not a complete config ready for the public internet. You still need to set up certificates, the TLS listener, the domain, and access policies yourself, and you must replace the example domain.

First make Hive listen only on loopback and generate the correct public links. If you don't need to run agents on the Server's computer, you can disable starting local agents from the web UI:

```bash
hive \
  --host 127.0.0.1 \
  --public-url https://hive.your-domain.com \
  --no-local-agents \
  --no-open
```

Add the following to the matching HTTPS `server` block in Nginx:

```nginx
location / {
    proxy_pass http://127.0.0.1:8787;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 3600s;
}
```

The web UI needs WebSocket, and agents also need HTTP / MCP. If you proxy only the home page and not these connections, you may see "the page loads but members are offline". The proxy and any outer platform must also allow your attachment sizes and long-lived connections.

:::caution[Don't disguise public requests as local ones]
Preserve the original public Host / Origin and the proxy source information. Don't rewrite them to localhost or remove origin checks just to make the local admin buttons work. Remote owners should use device sign-in and admin authorization; local-only capabilities have extra restrictions by design.
:::

This example has not been run on your network, certificates, or cloud platform. Before going live, verify the [security boundaries](/en/reference/security/), WebSocket reconnects, attachments, and remote agents one by one.

## Data and backups

The data directory in your startup options must live on persistent disk. If a container or ephemeral host is rebuilt without it, messages, rooms, and related configuration can be lost.

A backup should cover at least: the shared database, attachments, authentication- and encryption-related files, and local agent configuration. **Protect the entire directory as sensitive credentials**; never upload it to the docs site, a public repository, or a public room.

The simplest consistent backup procedure:

1. Notify the team and wait for or stop running tasks, checking external side effects first.
2. Stop the Server cleanly with `hive stop`; if you use a custom data directory, pass the same `--data-dir`.
3. Copy the complete data directory to a protected backup location, rather than copying only the SQLite main file while it's being written.
4. Restart with the original configuration, and rehearse restores regularly in an isolated environment.

A Server backup does not back up project files, Git history, or provider private sessions on each agent device. When restoring to a new device, don't assume old paths, CLI sign-ins, and local agent configuration will keep working.

## Updates, restarts, and keeping it running

- Only check whether a new version is available:

  ```bash
  hive update --check
  ```

- Upgrade to the latest version with the original package manager; a running Server restarts on the new version automatically:

  ```bash
  hive update
  ```

- Restart the current version only:

  ```bash
  hive restart
  ```

Both `hive update` and `hive restart` reuse the saved startup configuration; options passed explicitly to `restart` override it. During the restart the new Server takes over local Agents, so running tasks are not interrupted; if a handover isn't possible while tasks are running you're asked whether to wait or interrupt (scripts wait), and `--force` restarts right away. See the [CLI reference](/en/reference/cli/#updates-and-new-version-notices). When running via npx there is no `hive update`; use `npx superhive@latest restart` instead. For important environments, back up, read the release notes, and verify in an isolated environment before updating production. Don't treat development hot reload as a release process.

After a global install, `hive autostart on` starts it at login and `hive autostart status` checks the state. The path stays the same after `hive update`, so you usually don't need to re-enable it. Autostart is not a high-availability guarantee against every shutdown, sleep, or network issue. For a long-running service, use an always-on device and an explicit process management strategy.

Task recovery rules differ after a Server / agent restart or crash; see [Task states and safe recovery](/en/guides/tasks/). Don't use frequent restarts in place of troubleshooting, and don't rerun a task with external side effects just because you see "result unknown".
