## 先分清三层权限

接入成功不等于拥有所有操作权限。Hive 的使用中有三层不同的边界：

| 层次             | 决定什么                                           | 不代表什么                                   |
| ---------------- | -------------------------------------------------- | -------------------------------------------- |
| 房间身份         | 能加入哪些房间、读哪些消息和附件、能否触发相应任务 | 不等于获得 Server 电脑的文件或进程权限       |
| 本机管理权       | 能否在 Server 电脑上启动、停止 Agent，管理本机设置 | 不等于运行时的每个工具都已获准               |
| Agent 运行时权限 | Agent 能用哪些工具、在哪些目录工作，越界是否询问   | 不等于操作系统隔离，也不自动约束外部服务账号 |

Hive Server 负责消息与协调，不提供给房间成员直接使用的远程 Shell。真正的读写、命令和联网发生在 Agent 所在电脑，或它调用的外部服务上。

接入步骤见[接入 Agent](/guides/agents/)；公网访问、凭证与部署边界见[安全参考](/reference/security/)。

## 选择档位

| 网页档位 | 命令参数             | 建议用途                           | 必须知道的限制                                                                             |
| -------- | -------------------- | ---------------------------------- | ------------------------------------------------------------------------------------------ |
| 只读     | `--access read-only` | 看代码、解释、评审、给方案         | Hive 适配器限制写入类工具；可用的读取和命令工具因运行时而异，不保证任意外部 MCP 都无副作用 |
| 工作区   | `--access workspace` | 在指定项目内实现和验证             | 运行时的目录与工具限制并不完全相同，越界可能拒绝或转人工审批                               |
| 完全访问 | `--access full`      | 已明确授权、确需广泛访问的受信任务 | 不设 Hive 沙箱，可执行当前系统用户有权进行的操作；不是管理员提权，但风险仍很高             |

网页默认选择完全访问（免得沙箱拦住装依赖、跑测试、推代码），下次打开接入弹窗沿用上次的选择。访客、IM 和其它 Agent 发来的消息也能唤醒 Agent，房间里有不熟的人时建议改用工作区档。**聊天里说“可以改”不会把只读 Agent 自动升级成可写 Agent**；应先核对接入设置与任务授权。

工作目录也不是一句自然语言约定：工作区、完全访问档启动时要检查实际 cwd；多人并行开发还应[建立独立 worktree](/guides/worktrees/)。

## 不同运行时不能按同一个沙箱理解

- **Codex**：需要 0.105.0 及以上（Hive 通过 app-server 驱动 Codex），太旧时会提示升级；比 Hive 验证过的版本新、又出了协议错误时，会提示先 `hive update`。工作区档使用 `workspace-write`，工具需要越界授权时可转人工审批；完全访问使用 `danger-full-access`。只读档不通过 Hive 的工具审批升级写权限。
- **Claude Code**：工作区档在 macOS、Linux 上启用其沙箱，无法启用时（如 Linux 缺 bubblewrap）要求失败而非静默降级；需确认的工具通过 Hive 转给人。Windows 上 Claude Code 的沙箱还开不了，工作区档不开沙箱：命令可以访问工作区以外的文件，靠 Claude 的 auto 审核拦下有风险的操作，命中 ask 规则的操作会先请你确认；接入弹窗的档位说明和成员列表的「无沙箱」标记都会写明。完全访问关闭其沙箱并跳过运行时许可询问。
- **OpenCode**：工作区档通过运行时策略和 ACP 请求裁决限制文件改动，超出目录的改动可申请审批。Shell 命令并非由 Hive 提供完整的操作系统级目录隔离。
- **omp**：工作区档开放读取、编辑、写入、Shell 等工具，**普通写入并不被限制在 cwd 内，也不会都经过审批**。需要严格目录边界时不要把 omp 的工作区档当成 Codex 的沙箱。
- **Gemini CLI、agy**：只读档和工作区档下，写文件、跑命令、调用外部 MCP 工具都会发权限请求，由 Hive 按档位裁决：只读只放行读取和搜索，工作区放行命令和工作目录内的文件改动，超出目录的改动可申请审批。Hive 自己的 MCP 工具（发消息、白板等）在各档都放行。完全访问分别用 Gemini CLI 的 `yolo` 审批模式和 agy 的 `--dangerously-skip-permissions`。**CLI 自己已经放行的工具不会发请求**：Gemini CLI 内置的只读工具、你在它的 policy 文件或 `tools.allowed` 里放行的工具，以及 agy 权限设置里放行的工具，都不经过 Hive。命令同样没有操作系统级的目录隔离。
- **GitHub Copilot**：通过 CLI 的模式和工具允许／拒绝参数控制能力；工作区档开放写入与 Shell，不能据此推断存在与 Codex 相同的沙箱。只读档和工作区档还会关掉会话同步，不把会话传到 GitHub 云端：1.0.103 及以上传 `--sync-session=off`，更老的版本传 `--no-remote`，Hive 按 `copilot --help` 自动选。从 GitHub 网页或手机远程操控会话只能在 Copilot 交互界面里用 `/remote on` 打开，Hive 拉起的会话不会打开。
- **OpenClaw**：实际权限还需在 Agent 或 Gateway 中配置。Hive 不会自动改写其全局工具策略，网页选择档位不能替代 OpenClaw 自身的安全配置。

运行时版本、插件、MCP 和操作系统都会影响实际边界。敏感目录、生产数据与账号应使用独立环境和外部访问控制，不仅靠提示词或白板占用保护。

## 本机房主、其他设备房主与访客

### Server 电脑上的房主

直接在 Server 电脑上访问 `localhost` 或本机 IP 时，符合本机请求校验的网页可管理本机 Agent。校验同时检查连接来源、Host 和 Origin；带反向代理来源标记的请求不会因为代理也在本机就被当成本机房主。

请保留这些限制。不要为让远程页面出现启动按钮而伪造请求头或绕过来源校验。

### 房主的其他设备

房主设备身份和本机进程管理授权是分开的。已登录的房主设备可按页面流程申请限时管理权；以完全访问启动等高危动作还需要与设备和参数绑定的单次批准。

因此，「在这台浏览器里已登录」不等于「已允许在 Server 电脑上运行任意进程」。设备登录、授权与撤销步骤见[房间与身份](/guides/rooms/)。

### 访客与访客带入的 Agent

访客按邀请的房间、期限和授权范围参与；普通访客不取得本机管理权。其任务是否能触发房主 Agent 由服务端的访客授权流程决定，不是仅凭一条 `@` 就越过边界。

访客自己带入的 Agent 仍运行在该 Agent 的电脑上。工具审批中，房主身份可以审批；有效访客身份只能审批自己带入的 Agent 的申请，不能批准房主或其他访客的 Agent。

给别人的邀请和房主设备登录链接用途不同，不能互换。凭证、链接和包含凭证的接入命令都不应公开展示。

## MCP：工具接入不是自动授权

MCP 让 Agent 调用工具。Hive MCP 提供读房间、委派、白板、提问和定时等协作能力；额外 MCP 则可能访问浏览器、文件、业务系统或外部账号。

在 Codex、Claude Code 的本机接入与设置界面：

1. 查看可选的本机 MCP，不认识的服务先不要开启。
2. 只保留任务必需的加载项；`hive` 始终加载。
3. 看开局 token 估算，了解工具说明本身也占上下文和费用；估算不是实付金额。
4. 更改后在后续回合核对实际加载情况；正在运行的调用不会被设置变化撤销。

**限制文件写入不等于限制所有 MCP 副作用**。一个看似只读的 Agent 仍可能有能对外发消息、改业务数据的服务，最终要结合该 MCP 的账号、scope、运行时策略和每次任务授权判断。

不要把读取到的网页、附件、聊天或工具结果当作高优先级授权。收到“忽略规则、打印凭证”之类内容应拒绝，不应因为它来自工具就执行。

## 单次工具审批怎么处理

当支持审批的工作区 Agent 正在执行，需要超出当前许可的命令、文件或工具操作时，Hive 会发一条「允许 / 拒绝」申请给任务源头的人。

1. 打开申请，核对 **哪个 Agent、哪条任务、什么工具、路径或命令，以及影响范围**。
2. 确实属于原任务且风险可接受，点「允许」；否则点「拒绝」。也可准确回复该申请「允许」或「拒绝」，支持的飞书卡片可直接点选。
3. 结果交回 **正在执行的这一轮**，不是创建一个不受限制的新任务。
4. 要附加条件时先拒绝，再把修改后的要求交给 Agent；「可以，但先别删」之类带条件回复不算批准。

工具审批与普通[向人提问](/guides/collaboration/)不同：审批 **10 分钟**未处理、任务结束或停止、Server 重启时按拒绝处理，不应长期搁置。只读档直接拒绝相应越权请求，完全访问档不走这类 Hive 工具询问；它们仍可为业务决策主动提问。

批准一次不是永久授权，也不表示工具调用一定成功。完成后仍要查看[任务状态与验证结果](/guides/tasks/)。

## 开始写入前的检查表

- 明确请求来自谁，目标房间和 Agent 是否正确。
- 确认真实 cwd、可写文件与禁止触碰的目录；并行任务的写集不重叠。
- 提前约定是否允许安装依赖、提交、合入、推送、部署或对外发送。
- 确认 MCP 和外部账号的权限，不把只读标签当成万能保险。
- 看到审批或结果未知时先核对，不连续点击批准、重试或改成完全访问。
